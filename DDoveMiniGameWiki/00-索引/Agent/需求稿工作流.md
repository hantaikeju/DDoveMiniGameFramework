# 需求稿工作流

Concept ID：`/00-索引/Agent/需求稿工作流`。地图：[Agent 总览](/00-索引/Agent/Agent总览.md)。

`status` 只允许 `draft` / `stable` / `deprecated`。处理中 = 篇在 `05-需求`，且 `draft`，且 `tags` 含 `需求`。`/ddove-grill`：这句话写了目标就拷问这句，不数处理中的稿，不改已有稿。句中已有目标不用前文替换。只有命令时，接上发出这条命令之前用户已经说清的最近一条，再进入拷问。前文也没有已经说清的目标，才停下问要问什么。`/ddove-grill-with-demand` 才选已有稿：只有一篇直接做；多于一篇且没点名就停，只问选哪一篇；点了名只做那篇；没有则指向 `/ddove-grill`。`ddove-work` 改代码不数稿，只做本条对话当前 grill 的那一篇（`/ddove-grill` 刚落的稿，或 `/ddove-grill-with-demand` 刚选中的稿）；没有则停并指向 `/ddove-grill`。`/ddove-wiki-create`、`/ddove-fix-up`、`/ddove-wiki-change-state` 仍按篇数：只有一篇直接做；多于一篇只做点名的那篇；没点名就停，只问选哪一篇。开工只拆这一篇；回写和记分只落在这一篇。问答和排障不问选哪一篇。正文不自报 `status`，细则：[开篇与清单徽章](/00-索引/Agent/开篇与清单徽章.md)。

需求稿一律落 `05-需求`。`tags` 含目标职种（`策划` / `程序-前` / `程序-后` / `美术`，或 AI 用法的 `索引` + `agent`）以及 `需求`。`01`–`04` 与 `00-索引/Agent` 只放用法篇。

每一轮开工的得分表只追加到这一篇的 `## 评分`。不另开评分文件。尺子仍是 [开工评分](/00-索引/Agent/开工评分.md)；只有尺子条文要变才改那一篇。

## 步骤

1. `/ddove-grill`：这句话写了目标就拷问这句，不数处理中的稿。句中已有目标不用前文替换。只有命令时，接上发出这条命令之前用户已经说清的最近一条。前文也没有已经说清的目标，才停下问要问什么。验收要有证明方式，「要什么」要有变更种类。frontier 空则同一条对话里复述并落稿，然后停下。开工等人另发 `/ddove-work`。落稿不报成用户的下一步。不问短号。补充的新目标下次再 `/ddove-grill`。已有稿用 `/ddove-grill-with-demand`，问完按这篇开工，不另建第二份。`ddove-work` 改代码不数稿，只做这一篇；本条对话里没有当前 grill 的稿则停，并指向 `/ddove-grill`。
2. 代理落稿。目录 `05-需求`；`type: Playbook`；`status: draft`；`tags` 按上一节。不写 `generated.by`。开篇不写「本篇是 draft」。落在 `05-需求` 时调用 `ddove-show-me`（种类「说明页」），开篇加同目录相对链接，可见文字「打开说明」，打开同名 `.html`。手续读 `ddove-wiki-create`。
3. 人另发 `/ddove-work` 后按这一篇开工。走 `ddove-work`（先检索）。拆图先给两份公开接口，父会话冻结一份。开工只拆这一篇；回写和记分只落在这一篇的 `## 评分`。已有用法篇过期则改正文（回 `draft`、摘 `verified`）。改正文且旁边已有同名 HTML 时调用 `ddove-show-me`（种类「说明页」）重画这一张。问答和排障不走本收口，也不问选哪一篇。
4. 文件做完，代理立刻写状态，不等人先点头。用法篇按职种生成或改写：`策划` → `01-策划`；`程序-前` → `02-程序-前`；`程序-后` → `03-程序-后`；`美术` → `04-美术`；只有 `索引` + `agent` → `00-索引/Agent`。同一文件名，只写三块：干什么、有哪些接口、每个接口干什么。`tags` 无 `需求`。`status: stable`，`verified` 只写时刻。需求稿改为 `deprecated`，写入 `deprecated_at`，连同名 `.html` 搬到 `_archive/需求/`，原路径不留文件。正文留下 `## 要什么`、`## 不要`、`## 评分`、用法篇链接和「打开说明」；不留 `## 验收`、`## 落点`。`title` 仍含「需求稿」。手续读 `ddove-wiki-change-state`。本轮改过正文的篇在这一拍写成 `stable`，`verified` 只写时刻，清单去掉 `draft`。人不处理这些状态。然后给人看产品，顺序是用法篇、说明页、是否符合对齐需求，客户端再写运行证据或「未进 Play」，得分表在后。
5. 产品不对：人用自己的话指出要改的地方。代理把用法篇和需求稿都回到处理中（用法篇回 `draft` 并摘 `verified`，需求稿回 `draft` 且仍带 `需求`），改完再按第 4 步写上，再给人看。手续读 `ddove-fix-up`。
